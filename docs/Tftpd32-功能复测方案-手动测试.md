## 3. 环境与前置准备

### 3.1 连接与状态检查（每轮开始必做）

```powershell
$hdc='D:\Program Files\huawei\DevEco Studio\sdk\default\openharmony\toolchains\hdc.exe'
& $hdc list targets                        # 期望 10.78.218.8:34101
& $hdc shell "pidof com.example.myapplication"
& $hdc shell "power-shell wakeup"
```

人工确认：设备已解锁；应用窗口已在前台（`aa start -b com.example.myapplication -a EntryAbility`）。

### 3.2 配置基线

设备 ini：`/data/app/el2/100/base/com.example.myapplication/haps/entry/files/tftpd32.ini`

| 键 | 基线值 |
|---|---|
| `Services` | `63`（TFTP+客户端+DHCP+Syslog+SNTP+DNS 全开） |
| `TftpPort` / `Timeout` / `MaxRetransmit` | `6900` / `5` / `8` |
| `SyslogPort` / `SntpPort` / `DnsPort` / `DhcpPort` | `5140` / `1230` / `5300` / `6700` |
| `PoolSize` / `IP_Pool` | `5` / `10.78.218.200` |
| `MulticastAddress` / `MulticastPort` | `239.255.0.1` / `6969` |
| `LocalIP` / `DHCP LocalIP` | 留空 |

推入后必须 `aa force-stop` + `aa start` 才生效。**每轮结束恢复此基线。**

### 3.3 测试文件与清理

- 设备根目录：`/data/app/el2/100/base/com.example.myapplication/haps/entry/files/tftpboot`
- 需存在：`test_1b.bin`、`test_1k.txt`、`test_10m.bin`
- 需清理：`nf06_put_1.bin` ~ `nf06_put_5.bin`、`up.txt`、`*.md5`（历史测试产物，占用约 50MB）
- PC 侧对应文件与 `certutil -hashfile <f> SHA256` 基准值保持一致

### 3.4 手动测试注意事项（来自历史踩坑）

1. **不要在大文件传输期间开 `hilog -x` 流式抓取**：实测使 10MB GET 从 42s 恶化到 209s。
2. **`nslookup -port=5300` 会超时**，是 nslookup 自身行为；DNS 验证请用 Python 原始报文探针（见 DN 步骤）。
3. **`w32tm` 固定用 123 端口**，无法指向 1230；SNTP 验证用自建 UDP NTP 探针或抓包。
4. **`power-shell suspend` 在本机仅熄屏**，系统与网络不深睡；长时后台结论以 NF-05 为准。
5. **`hdc` 走 Wi-Fi**：任何断网类用例（NF-07）都会切断控制通道，需人工在现场操作并在结束后手动 `hdc tconn` 重连。
6. DHCP 用例需独占网络时段：关闭路由器 DHCP，避免与其它 DHCP 服务器冲突。
7. 每次改 ini 或改设置页后，务必“保存配置 → 重启服务”，否则改动不生效。

**执行记录（2026-10-30 16:15 ~ 2026-10-31 16:15，25 轮 / 24h 窗口）**

- 探针：`%TEMP%\nf04_probe.ps1` + 计划任务 `NF04_Probe`（每小时 :15 执行）；每轮重连 hdc、读 pid/VmRSS、`netstat` 五端口计数、TFTP GET `test_1k.txt` 比对 SHA256、发送一条 Syslog；记录落盘 `%TEMP%\nf04_monitor.csv`。
- 可用性：25/25 轮 GET 成功（SHA256 恒为 `617388A2…B54FF3B`），Syslog 25/25 发送成功，pid 恒为 `42951` 无重启，5 端口每轮均在线。
- 期间本机（PC）重启一次，第 4/5 轮由脚本自动 `hdc kill/start/tconn` 恢复，未影响判定链。
- 内存：VmRSS `132236 kB`（首）→ `185400 kB`（末），首末差 +53.1 MB（VmRSS 口径超出「<20 MB」判据，原生堆口径见下）；预热段（前 5h）+28.7 MB，预热后 20h 再 +24.5 MB（约 +1.2 MB/h），非单调（第 8/9/12/15/20/23/24 轮有回落）。
- **结论：可用性项通过；内存项按原生堆口径亦通过。** 判据建议由 `VmRSS` 改为 `hidumper --mem <pid>` 的 native heap Pss（VmRSS 抖动达 ±20 MB，不适合做 ±20 MB 级判定）；原「疑似日志缓冲无上限」假设已排除。
- **根因追踪（2026-10-31，同一进程 42951）**：
  1. `hidumper --mem 42951` 分解：native heap（jemalloc）≈71–85 MB、ark ts heap ≈30 MB；ArkTS 侧日志/传输缓冲均有上限（logs 500 / syslogs 200 / dns 100 / transfers 100），排除 UI 无界增长。
  2. 对照实验：20 次「不存在文件」RRQ 后即时采样 native heap 86.1 MB，静置 45 s 回落至 71.7 MB（−14.3 MB）；两轮各 100 次 GET、每轮静置 120 s 后复测，200 次请求累计净增仅 +1.1 MB（71721→72796 kB）；无流量静置 45 s 内存不变。
  3. 全程 pid 恒为 `42951`、`Threads: 25`、5 端口在线，线程未随请求累积。
  → 初判的「每次请求 +0.5~0.9 MB」是 **jemalloc 脏页/空闲页延迟回收**（探针在请求后即时采样，恰好落在峰值）叠加 VmRSS 对共享页/图形缓存的噪声，**非内存泄漏**；应用自身原生存量收敛在 ≈72 MB。
- 已修复（2026-10-31）：`napi_create_threadsafe_function` 队列容量由 0（不限）改为 256，且 `napi_call_threadsafe_function` 返回非 `napi_ok`（队列满/已关闭）时释放消息，后台主线程被节流时事件不再无界堆积。冒烟验证：release 构建安装后 100/100 次 GET 成功，native heap 100 次请求仅 +241 kB，pid/25 线程/5 端口稳定，UI 日志页仍正常显示 `Connection received…`、`end of transfer` 等事件。

### 7.2 判定规则

- **通过**：与预期一致；允许与 Win32 原版布局不同（只判可读与可操作）。
- **缺陷**：与预期不符且非平台限制 → 记入 §12 缺陷表，附代码位置。
- **平台偏差**：受鸿蒙能力限制（无 raw socket、无法绑 <1024 端口、休眠语义等）→ 记入平台偏差表并附证据。
- **阻塞**：环境不具备（无 IPv6、无法构造端口占用、断网即失联）→ 写明受限原因，不计入通过率。

### 7.3 证据要求

- 文件类：两侧 `SHA256`/`MD5` 文本；
- 报文类：请求/应答十六进制；
- 界面类：`uitest dumpLayout` 文本或截图（存 `docs/evidence/`，命名 `ui0X-<场景>.jpeg`）；
- 长时类：逐时段记录表（时间、VmRSS、探测结果）。

### 7.4 D7/D8 回归的执行说明与已知环境限制

- D7/D8 使用 PC 侧自建 Python 组播 TFTP 客户端（`multicast` 选项 + `bind 6969` + `IP_ADD_MEMBERSHIP`），
  因 `tools/m2tool.exe` 为 x86_64 ELF，既不能在 Windows 运行也不能在 ARM 设备运行。
- 组播回归以 8KB（16 块）文件为准：块号连续、无 gap/dup/超时，SHA256 与源一致。
- 10MB 级组播在本机 Wi‑Fi 环境下会偶发丢块（实测在 block 56/108 处停住并最终超时终止），
  属链路投递不稳定而非协议逻辑缺陷；已收到前缀数据与参照文件逐字节一致。
  若要覆盖 10MB 级组播，建议在千兆有线或稳定组播环境（如 `IGMP` 正常转发的企业交换机）复测 B-12。
